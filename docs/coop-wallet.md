# Co-op souls and household copies

Co-op uses one durable receipt ledger per signed-in account. The shelf remains a local save, and cloud save retains one household copy per account. Multiple devices using that household share the account ledger; signing another account into the same local shelf does not create a shared wallet between accounts.

Before the first wager, the client saves an opening snapshot with its owner and receipt cursor. The server accepts that opening once. Subsequent ordinary game earnings and purchases are separate saved operations, rather than another opening balance.

A device whose local household has no matching opening cannot adopt an existing account's server balance or declare a second grant. Co-op offers **Open cloud save**. The existing cloud dialog lets the player choose between **Keep this device** and **Use the cloud copy**, retaining the other shelf as a safety copy for one week. Using the matching cloud household restores its opening, cursor and pending operations. The server refuses an unrelated local copy that would remove the existing opening or confirmed ordinary reward/purchase provenance, including after **Keep this device**. Both copies survive; local offline gameplay remains available, and **Use the cloud copy** restores that account's household. A copy choice never counts as game income.

## Saving and retrying

The central save boundary records genuine wallet and lifetime-earned changes in a journal. Each operation has a stable UUID, account owner, signed wallet delta and independently recorded earned amount. For example, earning100 and spending100 before one save produces delta0, earned100. Wallet, journal and checkpoint are persisted in one save. Failed persistent storage blocks opening or transmitting financial operations; retry retains the same IDs. Before creating the first server opening or sending ordinary game deltas, the client also acknowledges the complete household through the existing cloud save API. The saved body must contain the exact pending operations, opening and business state. Failed uploads or copy conflicts preserve the local journal and leave offline play available.

The adjustment contract is `coop_adjust(p_ops)` with at most100 `{id, delta, earned, detail?}` operations. The owner comes from authentication. The server stores an immutable `game` receipt with `source_id=id`; repeating that payload is harmless, while changing an existing operation is refused. Receipt pages expose `has_more` and `last_seq` and must be contiguous for their owner.

Save uploads and settlements take the same account lock before the save-row lock. A generic adjustment inspects the current complete household for its exact already-applied pending operation, rather than trusting an earlier upload acknowledgement. If another tab replaced that checkpoint first, settlement refuses without charging. After settlement, a stale upload that omits the confirmed operation or matching opening refuses without replacing the household. These server checks also protect against cached older clients. Known typed rewards retain their canonical replay path.

A matching ordinary pending operation already changed the local purse, so its server receipt only acknowledges it. A semantic reward proposal stores `preApplied:false`; its cash and cosmetic effects remain un-applied until its canonical receipt arrives. An older owned backup can replay a typed stake, hire, duel or known reward receipt once. An anonymous game receipt requires its matching already-applied operation; otherwise the client requests the complete cloud household before changing money or the cursor. Opening snapshots, pending operations, owner cursors and semantic reward histories are financial bookkeeping and are never pruned as recent activity.

Offline purchases can overtake a stake placed on another device. The local purse stays nonnegative and carries any unpaid debit as debt. Later receipts repay debt before giving spendable souls. The server may have a negative budget from genuine offline purchases; a new stake must still be fully funded. A missing debit is never erased merely because the restored local purse is empty.

Money alone is insufficient to restore ordinary gameplay. Replaying a weekly payment without its claimed flag can pay it again; replaying a purchase debit without its item can charge for a missing item. Every cloud push for a household with a recorded opening therefore performs a read-only financial preflight. Unknown anonymous game receipts stop both automatic and manual upload before the current cloud household can be overwritten. A backup from before opening also requires a read of the complete cloud household: when that account's cloud copy records an opening, normal upload stops for an explicit copy choice. This protects current-revision imports without requiring Co-op RPCs for accounts that never used Co-op. The existing copy-choice card, including its safety copy, restores the full household instead. `requestCopyChoice()` explicitly reads both copies even when the browser still knows the current cloud revision; it never treats an imported old backup as a newer source to upload.

## Rewards and restored state

Backend-idempotent rewards need more than an anonymous wallet delta. Their operation UUID derives from the owner and semantic source key using SHA-256 UUIDv8. The receipt also includes validated metadata that restores the paid marker and actual cosmetic award. This prevents restoring an old backup, replaying its currency receipt and collecting the same chest again.

Reward handlers rebuild markers and non-currency effects only; the receipt engine owns the money. Network rewards first save a pure proposal, then obtain the first immutable server award before changing cash, ranks, cosmetics or paid markers. Two devices may propose different next-unowned curios or duplicate-soul bonuses for the same source. The canonical first receipt settles both devices; the second proposal does not grant its speculative item or amount. Reconciliation downloads receipts before uploads and resolves a racing semantic `bad_op` by reading the canonical receipt before retrying remaining operations. Generic changed payloads are still refused. Pending metadata survives normalization before its feature controller loads.

An unreleased prototype may contain an already-applied semantic reward whose payload conflicts with the server’s original award. The client preserves that save and refuses to guess an inventory or currency rollback. Recovery requires the matching original cloud household or a backup from before the reward.

Replacing/importing a household rebases the currency checkpoint without interpreting the imported balance as an earning. Reconciliation and gameplay callbacks also capture the Co-op state object's identity, so an in-place restore under the same account cancels old work. Account changes prevent submitting or applying another owner's operations.

Unowned v1 prototype holds, attempts and reward marks are retained in quarantine. No account is guessed from whichever player happens to sign in. Co-op was not released with those prototype records; production rollout requires schema/data preflight rather than silently assigning them.
